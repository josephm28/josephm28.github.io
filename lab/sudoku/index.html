Solving sudoku without looking it up

A 2019 challenge: write a sudoku solver from first principles, then point it at the "world's hardest" sudoku.

Built August 2019 · JavaScript · Node.js

View the code on GitHub

The rule

Sudoku solvers are a classic programming exercise, and the well-known approaches are one search away. That was the problem. I wanted to see what I'd come up with on my own, so the repo's README states the rule up front: "Trying to build this without consulting other algorithms."

The commit history tells the rest. The first real commit is solving code as written in one file. I wrote the whole solver first, then pushed it on August 23, 2019, and spent the next 20 minutes or so tidying: moving the sample puzzles into a folder, splitting out helper functions, adding a license and a run script. Seven commits, about 160 lines of JavaScript.

How it works

It's the way a person solves sudoku with a pencil, made relentless. Look at an empty cell and ask which numbers could possibly go there.

One cell rarely solves a puzzle, so the solver sweeps the whole board, fills every cell it can, and repeats. Each number it writes in narrows the options for its neighbors, so easy puzzles fall apart in a few sweeps.

Harder puzzles get stuck: every empty cell has two or more candidates, and sweeping changes nothing. That's when it guesses. It snapshots the board, picks a cell with exactly two options, and tries one. If the guess is wrong, a later sweep finds a cell with no possible numbers, and the solver rolls back to the snapshot and tries the other option. Guesses can stack inside guesses, which makes it a depth-first search.

everest is Arto Inkala's puzzle, published in 2012 as the "world's hardest sudoku." My solver needs nearly a thousand dead ends to get through it, and it still finishes in a fraction of a second.

Then there's extreme, which the solver says can't be solved. I assumed that was a bug in the solver. It isn't. Row 7 of the puzzle file reads 0 0 0 7 0 7 0 0 0: two 7s in one row. I made a typo copying it in back in 2019, and the solver correctly reported that no solution exists.

Looking back

Without knowing it, I'd landed on the standard approach: rule out candidates using what's already on the board, and when that stalls, guess and backtrack. That's the same general shape as most textbook solvers. If I picked it back up, I'd:

  • Guess where it's cheapest. It guesses at the first cell with two options. Choosing the cell with the fewest options would prune the search faster, and it would handle a board where no cell has exactly two.
  • Keep candidates around. Every sweep recomputes each cell's options from scratch. Updating them only when a neighbor changes would cut most of the work.
  • Return the answer. The solver prints the finished board but only returns true or false, so nothing else can use the solution.
  • Check the puzzle first. A two-line check for duplicate givens would have caught the typo before any solving started.

The code is still exactly as I left it in 2019: github.com/josephm28/sudoku.
